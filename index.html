A BETTER RECORD OF THE DAY

From “what’s next?”
to “what happened?”

Planning tools capture intentions. Acorda explores the space between a plan and a trustworthy record of daily activity: brief audio, a photo, and a day view that brings them back into context.

Product goals

  • Make daily capture quick and user-initiated.
  • Keep personal photos and audio evidence on the device.
  • Separate an evidence record from task completion or confirmation.
  • Let access changes preserve evidence already saved.

Key decisions

  • Photo-First capture does not require a task to exist first.
  • Calma sessions should complete without an offer or interruption.
  • Free/Pro access is checked at the capability boundary, not just hidden in the UI.
  • Billing and purchase verification are later work; no commercial launch is claimed.

02DESIGNINTERACTION · STATES · EVIDENCE

DESIGN FOR THE MOMENT OF USE

Make the next action
obvious. Keep the record honest.

Acorda's interaction model centers on a selected day and short capture paths. The design distinguishes capture, save, review, and confirmation so a piece of media never silently becomes a completed task.

01 / CAPTURE

Start by choice

Voice and photo capture begin from an explicit user action, with visible ready, active, saved, and recovery states.

02 / REVIEW

Keep evidence in context

Agenda and history support a return to saved evidence without requiring the user to recreate the capture flow.

03 / ENTITLEMENT

Make access predictable

Locked capabilities should be clear before starting. A breathing session already in progress remains uninterrupted.

ENG
01
AGENDA QUERY SCALINGMEASURED · SYNTHETIC DATA

Stop searching history for a replacement on every card.

Problem

Agenda history ran a correlated replacement-recording lookup for each recording card, including older and already successful recordings.

Investigation

SQLite's query plan showed the replacement-status index lookup repeating per card. The behavior was isolated with synthetic histories and a Xiaomi 14T SQL harness.

Decision & implementation

Keep historical day reads focused on evidence. Use the original and newly saved IDs from the live re-record flow for replacement cleanup. No new index or Room migration was added.

Verification & lesson

Returned evidence fields and row order matched in the synthetic check. Query performance is not the same as full Compose screen latency; measure the layer that is actually slow.

Agenda SQL query · warm medianSQLite 3.44.5 · Xiaomi 14T · 7 measured runs / size
Previous query Revised query · 12.38–12.49 ms

Synthetic SQLite query benchmark only, using existing indexes. It is not a full-app, Room, or screen-render benchmark. Dataset and thermal/cache variation still matter.

ENG
02
CRASH-SAFE AUDIO RECOVERYSOURCE + TESTS

Recover interrupted capture without treating history as disposable.

Problem

Capture may end between file creation, Room persistence, and user-confirmed completion.

Decision

Journal temporary capture intent and clean only explicitly abandoned new captures. A failed recognition or old recording is not proof that saved evidence is invalid.

Verification

Recovery use cases are in the passing JVM suite. Room recovery and migration instrumentation tests compile; they were not among the 31 focused emulator tests in this checkpoint.

Lesson

Temporary-file cleanup needs ownership and consent rules that are separate from deleting committed evidence.

ENG
03
ROOM MIGRATION HISTORYSCHEMA V1–V6

Keep data evolution explicit.

Evidence

Room schema snapshots 1 through 6 and explicit migrations 1→2 through 5→6 are present in the private source history.

Decision

Preserve the user's evidence and add schema changes through migration paths rather than replacing the database.

Verification

Migration test sources compile. The focused emulator pass described here did not execute the migration test classes; a dedicated migration run remains a publication-quality evidence item.

Lesson

A passing compile is not a migration result. Test old snapshots through the actual Room migration runner.

ENG
04
ON-DEVICE SPEECHDEBUG + RELEASE SOURCE

Use the approved Android recognizer in both variants.

Decision

Debug and release source sets select `AndroidOnDeviceTranscriptionEngine`; the binding has no Whisper fallback. The engine uses Android's on-device `SpeechRecognizer` API.

Privacy

Speech processing is gated by product access. Free audio is saved without starting STT under the approved capability policy.

Verification

Source selection is verified. The 31-test focused emulator run did not measure recognition accuracy or cover a device language-model download.

Lesson

Engine selection, device availability, and recognition quality are distinct claims and need separate evidence.

ENG
05
CALMA ACCESS GATINGJVM TESTED · UI STATUS SEPARATE

Check entitlement when a breathing session starts.

Policy

Cyclic Sigh remains Free. Five additional patterns are Pro. An active in-memory session is not revoked mid-exercise.

Implementation

`StartBreathingSessionUseCase` enforces access at the domain boundary; the UI presents locked patterns before starting.

Verification

The domain use-case tests are included in the passing JVM suite. Calma Android UI behavior was not included in the 31 focused emulator cases cited here.

Lesson

Entitlement rules belong in the use case as well as the interaction layer.

SPOTLIGHT SEARCH TIMINGDEVELOPMENT LOG · SOURCE UNAVAILABLE

Do not treat an asynchronous search index as synchronous state.

Problem reported

Fast typing followed by Enter could use stale folder results and create a duplicate.

Investigation reported

The notes identify `NSMetadataQuery` as asynchronous and describe a debounce-related race.

Decision reported

A synchronous filesystem existence check was explored. Notes disagree on whether the final fix covered all pinned locations.

Verification boundary

No reproducible source or test artifact was found. This is a design/debugging lesson from notes, not a verified fix claim.

02
DRAG & DROP CONCURRENCYDEVELOPMENT LOG · SOURCE UNAVAILABLE

Disable UI controls and guard the actual event entry points.

Problem reported

Notes say SwiftUI's `.disabled()` did not block every gesture and drop callback.

Decision reported

The log describes explicit processing guards at interaction entry points and background I/O for slow routes.

Verification boundary

Notes report fixes and a local-to-network transfer exercise. The source and test setup are unavailable, so exact coverage cannot be confirmed.

Lesson

Concurrency safety belongs at the operation boundary, not only in the visual state of a control.
